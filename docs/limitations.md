# 边界与限制

本项目是**提交协议验证台**，不是生产湖表运行时。以下边界是设计选择，不是待办功能清单。

## 非生产定位

- 不兼容 Iceberg / Delta / Hudi 的元数据、清单或事务协议。
- 不读写真实 Parquet/ORC 数据文件；`content_hash` 是 fixture 的合成内容标识。
- 不连接对象存储、Hive Metastore、远程数据库、消息队列或任何第三方 API。
- 不提供 SQL、时间旅行、模式演进、分区演进、行级删除、权限系统或查询引擎。
- 不实现压缩、重写、小文件合并、快照过期、孤儿清理、保留策略。
- 不做性能基准、吞吐测试或故障注入；项目关注判定语义与可复现证据。

## “并发”的含义

- 没有真实并发线程或分布式调度。
- JSONL 的行序就是本验证台中的到达顺序；每个 attempt 顺序读取当前状态并判定。
- 这样可以稳定复现“多个 writer 基于不同 base 提交”的结果，但不能证明真实系统中的线程安全、锁竞争或网络分区行为。
- 不实现 CAS、租约、共识协议、两阶段提交或冲突解决协商。

## 一致性与崩溃恢复

- 快照目录先完整写入临时目录，再 rename 为不可变目录；`current` 通过临时文件 + `os.replace` 原子替换。
- 但“发布快照”“写 SQLite 审计台账”“写幂等首结果”不是一个跨存储事务。
- 进程若在快照发布后、台账/幂等缓存提交前崩溃，可能出现快照可达但台账缺失，或幂等缓存缺失的状态。`verify` 能发现部分结构性异常（如不可达快照），但不做自动修复。
- 没有 WAL 协调、恢复日志、幂等补偿任务或崩溃一致性测试。
- `verify` 检查：current 可解析、parent/sequence 连续、文件清单哈希、commit 中 snapshot/sequence/parent 一致、路径唯一、无不可达快照目录。
- `verify` 不重新计算或验证所有 commit 字段，不验证 commit 的密码学签名，也不检测恶意同时改写 manifest 与 commit 的攻击。

## 幂等缓存边界

- 幂等作用域固定为 `(writer_id, idempotency_key)`，没有租户、表或客户端实例维度；不同表共用同一工作目录时会互相影响。
- 载荷身份只含 `base_snapshot_id + operation`；attempt id 与逻辑时间被有意排除。
- 首次判定会缓存，包括冲突拒绝；结构校验失败不缓存。
- 幂等缓存与快照状态分离；若外部手工修改快照目录，缓存中的 `resulting_snapshot_id` 可能指向不可达或已变化的状态。
- 重放返回首次结果，不重新执行 rebase 或重新检查当前分区；这是幂等语义，不是“重新判定”。
- SQLite 文件是本机明文状态，无加密、无访问控制、无防篡改保证。

## 文件与路径

- 文件路径是**逻辑路径**，不会在磁盘上创建对应数据文件。
- 路径校验拒绝绝对路径、`..`、反斜杠、盘符、URL；这降低了路径穿越风险，但也意味着某些合法对象存储键无法表达。
- 路径比较是大小写敏感的字符串比较；不模拟不同文件系统的大小写折叠或 Unicode 规范化。
- 不允许重复路径；不实现同一路径的“覆盖提交”，需使用替换操作。
- `replace_partition` 要求替换文件非空，因此不能通过该操作把分区清空。
- `replace_file_set` 的 expected 文件必须存在于 base；不支持任意批量删除或“只增不删”的隐式集合。
- 分区列和分区值是不可变声明；不支持分区演进或运行时新增分区列。

## rebase 与冲突判定

- 只接受可证明安全的情况：新增路径无重复且目标分区未被触碰；陈旧分区替换的目标分区未被触碰；文件集合替换的 expected 文件指纹未变。
- 这不是通用三方合并；不执行内容级 merge、重命名检测或冲突自动解决。
- 被拒绝的提交不会写入快照目录，只保留 attempt 级审计记录。
- 冲突码稳定，但 reason 的英文描述文本不承诺逐字稳定；golden 会锁定当前文案。
- `STALE_BASE_REBASE_DISABLED` 仅在协议配置显式关闭安全 rebase 时出现；默认允许。
- 陈旧 base 上的 `add_files` 与 `replace_partition` 可能产生多个冲突码（例如同时记录 `REPLACE_PARTITION_CONFLICT` 与 `PARTITION_TOUCHED_SINCE_BASE`），调用方应按集合处理，而不是假定单一码。

## 报告与确定性

- 确定性依赖固定的 fixture、相同 Python/PyYAML/Flask 版本、稳定的文件系统枚举与 JSON 序列化行为。
- 报告不含系统时间、随机 UUID、绝对工作目录；但 `run.json` 是运行元数据，不属于稳定 golden。
- snapshot id 是内容相关的确定性哈希，不是全局唯一 ID；不同工作目录中的相同输入会得到相同 id。
- 逻辑时间只做格式和单调叙事使用，不读系统时钟；不验证真实时区或日历合法性超出格式范围。
- HTML 自包含、无 JS；它适合本地审阅，不是仪表盘产品。
- 报告大小随场景线性增长；没有分页、流式输出或大结果集优化。

## 只读复核台

- 仅允许绑定 `127.0.0.1`、`localhost`、`::1`；这不是互联网服务。
- 无身份认证、授权、TLS、CSRF 或审计日志；安全边界是“只在本机回环、只读、合成数据”。
- 只注册 GET/HEAD，写方法返回 405；没有上传、编辑或触发重跑能力。
- 服务读取工作目录现有报告和 SQLite；报告不存在时返回稳定错误，不会自动运行协议。
- 不保证多进程同时写工作目录的安全；同一 workdir 应由单个运行器使用。

## 规模与依赖

- 总代码预算 2500–4500 行、单文件 ≤300 行，这会限制功能广度；新增能力前需先评估预算。
- 运行期第三方依赖仅 PyYAML 与 Flask；Flask 开发服务器不是生产 WSGI 部署方案。
- 未在多种操作系统/文件系统上做兼容性矩阵；本项目在 Windows 上开发验证，路径以 POSIX 风格逻辑路径表达。
- 不支持 Python 3.9 及以下。
- 未实现插件、扩展点或外部存储适配器。

## 明确的非目标

以下能力即使与湖表相关，也不在本项目范围内：

- 真实事务提交与回滚、快照回滚、按时间查询；
- 多表 catalog、跨表事务、表重命名；
- 数据文件校验、压缩、编码、统计信息收集；
- 写入配额、限流、优先级、多租户隔离；
- 生产级监控、告警、指标导出、分布式追踪；
- 恶意输入下的强化沙箱或资源隔离。

需要这些能力时，应把本项目当作协议语义测试夹具，而不是直接扩展为生产服务。
